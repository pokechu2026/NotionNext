01 — THE PROBLEM

問題不在曝光不足
在於價值來不及被理解

貴司提出的核心課題是：消費者沿用既有的家具購買習慣來理解 MOOYU，看不見家配師的判斷過程，尚未理解價值就進入服務流程，導致雙方對服務的期待無法對焦。

這個描述指向的不是知名度問題。以 15–50 萬的客單價與一至三個月的決策週期而言，衝曝光無法解決理解落差——而理解落差正是內容可以處理的問題。

09/04 通話・我方筆記整理
  • 90 分鐘家配諮詢的價值，多數來客在接觸之前並不清楚
  • 官網該篇服務說明文章的觀看率偏低
  • 過去曾嘗試主動溝通服務價值，成效有限
  • 使用者在官網實際會看的是商品案例與門市資訊
  • 相對受歡迎的內容型態偏向「十大推薦」「怎麼選家具」這類

以上為我方依通話內容整理之筆記，如有理解偏差請不吝指正。

結論不是「內容無效」，而是「主動教育無效」。

主動教育的前提，是對方願意先停下來聽完一段說明。多數正在挑家具的人並不在這個狀態——他們有一個具體而急迫的問題要解決。

海巡不需要這個前提。它不解釋、不鋪陳，只在對方已經開口問「三米二的牆放三人座會不會太擠」的那一刻，給出一個真正有用的答案。價值不是被宣告的，是在回答問題的過程裡被看見的。

本案要驗證的問題

因此第一階段不驗證「內容能不能經營」，而是一個更窄、可以被證偽的問題：

  • Threads 上是否存在足夠密度、正在做家具決定且位於服務範圍內的人？
  • 以現有條件，這些人找不找得到？
  • 介入之後，對話推不推得動、願不願意進入貴司既有的服務流程？

三個問題有答案，就足以判斷 Threads 值不值得繼續投入。

02 — TARGET

目標客群的判定結構

依貴司提供的 TA 條件，將「值得介入」拆解為可判定的訊號，並以服務範圍作為不可跨越的硬篩。

地區是最貴的隱形成本

條件符合者可能有相當比例位於服務範圍外，直接作廢。此損耗已計入後續所有數字，不另行樂觀估計。

To B 只觀察，不設 KPI

Threads 上 B2B 密度低，設計師與建商不在此談案子；且貴司已有家配師獨立開發的 To B 路徑。第一階段僅記錄，避免稀釋 To C 樣本。

03 — THE SYSTEM

五個動作的作業系統
機器負責判讀，人負責說話

海巡不是「刷 Threads 回留言」。它是一條每日要跑完五個動作的流程。量最大、最重複的兩格由模型承擔；最需要判斷力與語感的兩格由人承擔，並且不可自動化。

以下逐格展開各階段的細部流程與技術配置。

01 找搜出符合條件的貼文｜每工作日 15–20 則 系統人
  • 關鍵字矩陣：品項（沙發／餐桌／床架／櫃體）× 情境（交屋／裝修／搬家／換屋）× 空間語彙（坪數／米數／格局／動線）× 地區詞，交叉展開為每日輪替的檢索組合
  • 檢索以人工為主線：每日 15–20 則的量在人力射程內，本案 KPI 亦以此為基準
  • 另有一項官方技術可放大此格效率：詳見第 04 節「技術補充」。該項需平台審核，不列為本案執行條件
  • 去重與冷卻：已介入帳號記錄於資料表，避免重複打擾同一使用者
02 判是否為真需求、地區是否符合、急不急 AI 初篩人複核
  • 判讀模型：以貴司 TA 條件建構分類器，輸入貼文全文與留言脈絡，輸出符合與否、需求類型、地區線索、急迫度、可切入點、優先序
  • 輸出即排序：每日候選清單依優先序排列，人力集中於前段而非平均分配。這是整條流程效率槓桿最大的一格
  • 人複核不可省：模型負責篩掉明顯不符者並排序，是否介入由人決定。誤判的成本是打擾真實使用者，不交由機器承擔
  • 判準可調：第 5 個工作日依實際密度回頭調整寬窄，模型與搜尋條件同步更新
03 介入寫一則不像業配的留言 AI 起草發送絕不自動
  • 三項輸入：貼文脈絡與判讀欄位 ＋ 貴司品牌語氣參數（溫暖不煽情、專業不炫耀、節制不冷淡、具體不抽象）＋ 家配專業知識庫
  • 知識庫來源：貴司提供之品牌內容與案例、家配師常見誤解問答、實際案例的預算配置邏輯
  • 人改人發：草稿一律改寫後由人發送。罐頭留言在 Threads 上會被瞬間辨識，且可能被平台降觸及——語感是這格唯一真正值錢的東西
  • 開工前先對齊：提供 10–15 則模擬情境與回覆草稿供貴司確認語氣，通過後才開跑
04 推進留言 → 私訊 → 交棒家配師 純人工
  • 對話推進至可辨識需求（地區、品項、時程明確）後交棒，並附上對話摘要與判讀欄位，家配師不必從頭問起
  • 交棒是整條流程的斷點：此後的回應速度不在我方控制範圍內，卻直接決定該筆樣本是否有效。詳見第 07 節配合事項第一項
  • 此格無任何自動化。信任是在真實對話裡建立的，因此這一格由人全程負責，也是本案最看重的環節
05 記錄逐格記下漏斗，判讀與結案報告自此產生 結構化人
  • 怎麼標註：每完成一個動作——送出留言、收到回應、進入實質討論、完成交棒——即於當下記錄時間戳與狀態，不事後補登。回應時間差是本案的關鍵指標之一，事後回填會失真
  • 標註什麼：日期／貼文連結／判讀結果／需求類型／地區／介入時間／留言內容／是否回應／回應時間／是否進入實質討論／是否辨識為有效需求／交棒時間／家配師回應時間／後續狀態，共 14 欄
  • 會得到什麼：由這 14 欄可直接算出——各段轉換率與流失最嚴重的一格、平均回應時間、哪一類需求最容易推進、哪些關鍵字組合的產出效率最高、交棒後的回應時效如何影響成案率
  • 為什麼重要：這些數字構成結案報告的判斷依據，也是續行時「該把力氣放在哪裡」的配置建議來源。每一個數字都能點回原始貼文與對話，不是彙總出來的印象
  • 每週自資料表產出判讀報告；月末產出結案報告與後續配置建議

平台理解與系統優勢

海巡之所以在 Threads 可行，是因為這個平台的擴散結構與其他社群不同。以下前兩項是平台機制，後四項是系統設計上的取捨。

擴散靠留言串，不靠發文

Threads 上一則有內容的回覆會把原貼文與回覆者一併再推一次。這使「留言介入」不只是接觸單一使用者，同時取得該串的曝光——這是發文型內容做不到的。

推銷語句會被結構性壓低

制式、明顯導流的留言在此平台的觸及衰減明顯。因此「逐則改寫」不是道德要求，是機制要求；批次貼文只會讓帳號愈打愈冷。

排序，而非平均分配

模型的價值不在寫字，在於讓有限人力集中在最可能成立的前段名單，而不是平均消耗在三百則貼文上。

語氣可控且可稽核

語氣先對齊、話術庫成文、每則留言留存。品質不依賴當天的狀態，出現偏差可以指出是哪一則、哪一句。

結論可回溯

結案報告的每個數字都能點回原始貼文。這決定貴司能不能真的拿它做決策，而不是看一份感想。

可交接，不綁人

SOP、判讀標準與話術庫皆為文件。貴司內容行銷企劃到職後可直接承接，不需重新摸索三個月。

04 — TECHNICAL NOTE

技術補充
Threads 官方關鍵字檢索 API

此項目未在 09/04 的通話中討論。是我方在準備本提案期間，為了解決「檢索效率」這一格而另行研究、並確認可行的官方技術。因為它可能改變第二個月之後的執行規模，因此在此完整說明。

它是什麼

Meta 於 Threads 官方 API 中開放的關鍵字檢索端點（keyword_search）。它允許以關鍵字檢索平台上的公開貼文，是目前唯一合法、不違反平台條款的程式化檢索途徑。

項目內容
可以做以關鍵字、主題標籤檢索公開貼文；可依媒體型態（文字／圖片／影片）篩選
不能做無法對他人貼文留言、無法發送私訊。介入這一格在技術上就無法自動化——這也是我方在第 06 節將自動留言列為紅線的原因
額度每 24 小時 2,200 次查詢，另有每 7 日 500 次上限；無結果的查詢不計入
取得條件需通過 Meta 對 threads_keyword_search 權限的審核。未通過前僅能檢索自有帳號的貼文，無法用於本案
審核期程依公開資料，權限審核本身約 3–5 個工作日；但完整流程另含企業驗證與存取驗證，實務上自送件至通過多落在 1–3 週，若需補件會再延長，且不保證通過

技術示意

檢索以單一端點取得結構化結果，可直接接入本案的判讀流程，不需人工複製貼上。

REQUEST

GET /v1.0/keyword_search
  ?q="交屋 沙發 三人座"
  &search_type=TOP
  &fields=id,text,permalink,
          timestamp,username
  &access_token={token}
關鍵字由矩陣自動展開，每日輪替送出。

RESPONSE

{ "data": [
  {
    "id": "178414...",
    "text": "下週交屋…三米二…有貓",
    "permalink": "https://…",
    "timestamp": "2026-09-06T…"
  } ] }
回傳即為結構化資料，直接進入判讀模型。

結果

貼文連結、原文與時間戳一次取得，省去人工逐則翻找與複製；同一組關鍵字可穩定回溯較長區間，減少漏接。
此為端點用法示意，實際欄位以 Meta 官方文件為準。

官方途徑與非官方工具的差別

網路上流通著數個逆向工程的第三方套件，宣稱可繞過審核直接取用 Threads 資料，部分甚至提供自動留言功能。此處一併說明我方不採用的理由。

官方 API（我方採用）非官方逆向套件
合規性Meta 官方端點，符合平台條款違反平台使用條款
取得速度需 1–3 週審核即刻可用
帳號風險無停權風險由品牌帳號承擔
穩定性由 Meta 維護平台一改版即失效
留言與私訊不支援，一律人工部分套件支援自動化，屬高風險操作

對本案的意義

以每日 10–20 組關鍵字計算，額度綽綽有餘。真正的差別在覆蓋率與速度——人工檢索受限於逐則翻看的時間，能掃到的是熱門與近期貼文；API 可讓關鍵字矩陣完整輪替、並穩定回溯較長時間區間。

本案基準（人工檢索）權限通過後
每日候選量15–20 則可穩定放大，並提高服務範圍內的命中比例
關鍵字覆蓋每日輪替部分組合矩陣可完整跑完，減少漏接
人力配置時間分散在「找」與「判」可集中於介入與對話品質

我方的處理方式

  1. 本案啟動後，協助貴司提出申請以貴司官方帳號為主體申請權限，我方負責技術文件、用途說明與串接測試，不另計費用。此為附帶價值，非本案報價項目。
  2. 但不納入本案的執行條件平台審核期程不可控，可能數週亦可能更久。因此本案的 KPI、期程與報價，全部以人工檢索可達成的量能為基準設定；權限若於期間內通過，視為超額收穫，若未通過，不影響任何承諾。
  3. 通過後的效益歸貴司權限掛在貴司帳號下，即使日後合作結束，該能力仍留在貴司，可由內部人員或後續配合的團隊繼續使用。

為什麼特別提這一項

市面上多數社群操作服務，若要放大檢索量，會走非官方爬蟲或自動化工具——那些方案短期看起來更快，但風險由品牌帳號承擔。我方選擇的是官方途徑，代價是要等審核，換到的是零停權風險，以及一個留在貴司手上的長期資產。

關於指標未達成的處理

若第一層的執行標準未達成，屬我方履約瑕疵，願依比例調整報酬。若第一層達成、第二層數字未達假設值，代表 Threads 上的需求密度不如預期——這正是本案要驗證的問題，其結論本身即為交付成果，不構成減價事由。

此原則建議於合約中明列，以免執行期間對「是否達標」產生認知落差。

為什麼不把成交列為 KPI

貴司平均成交週期一至三個月、訂製交期 30–45 天。一個月內留言、同月內成交，在這個生意的節奏裡不成立。把成交設為 PoC 指標，只會逼出短打，那對品牌是傷害，數據也無法判讀。

而依通話所述，貴司上月接待與成交的轉換約在兩成——人只要進得到店，後段是有效率的。本案要證明的是「進得來」，不是「成得了」。
